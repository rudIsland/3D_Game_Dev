# 작업 규칙

## 요청과 근거

1. 요청, 현재 코드 구조, 예상 동작을 먼저 검토한다. 근거 없이 동의하거나 완료로 단정하지 않는다.
2. 질문이 여러 의미라면 이해한 핵심을 짧게 설명한다. 파일 삭제·복원처럼 범위가 크게 달라질 때는 확인한다.
3. 전제가 틀렸거나 이전 설명과 모순되면 근거와 함께 바로 정정한다.
4. 입력 → 처리 → 출력·저장·응답 순서로 설명한다. 문제의 원인과 수정 방향을 함께 제시한다.
5. 동시 작업 중인 변경을 임의로 되돌리거나 정리하지 않는다. 사용자에게 이미 받은 작업 범위와 지시를 따른다.

## 지시한 범위만 수행

1. 사용자가 지시한 내용만 작업 목표로 삼는다. 요청하지 않은 기능, 편의 도구, 추상화, 구조 변경이나 다른 객체로의 적용을 임의로 목표에 추가하지 않는다.
2. 함께 수정할 수 있는 범위는 요청한 결과가 정상 동작하는 데 반드시 필요한 호출부·정리 경로·검증과 프로젝트 규칙상 문서 갱신까지다. 해당 변경 없이도 요청을 충족할 수 있다면 필수 작업으로 취급하지 않는다.
3. 개선 가능성이나 미래 확장성을 근거로 범위를 넓히지 않는다. 추가 제안은 현재 작업과 구분하고, 사용자가 명시적으로 승인하기 전에는 구현하지 않는다.
4. 사용자가 범위를 줄이거나 되돌리라고 하면 이전 계획보다 최신 지시를 우선한다. 취소한 기능을 이름이나 형태만 바꿔 다시 추가하지 않는다.

## 코드 수정

1. 사용자가 명확하게 “수정해”, “적용해”, “진행해”라고 요청한 경우에만 실제 코드를 수정한다.
2. 코드 수정 전에는 현재 동작 순서, 문제점, 수정 대상, 수정 이유, 예상 변경 범위와 변경 전후 코드를 먼저 설명한다.
3. 분석, 검토, 설명 요청에서는 파일을 수정하지 않는다.
4. 기존 동작을 유지하면서 작은 단위로 점진적으로 수정한다.

## 공통 작업 순서

1. **범위 확인:** 설명·검토, 실제 수정, 실행 연결, 에셋 등록 중 요청한 결과를 구분한다. “등록”을 자동 생성·실행 구현으로 확대하지 않는다. 이미 승인된 변경은 설명 후 진행하며 같은 범위의 승인을 반복해서 묻지 않는다.
2. **근거 확인:** 최근 세션과 Git 상태, 대상 README, 실제 코드·씬·프리팹을 읽는다. 요청을 받는 곳 → 처리하는 곳 → 상태·리소스를 가진 곳 → 결과를 쓰는 곳 → 반환하는 곳을 추적한다. 파일이나 클래스가 있다는 사실과 실제 호출·실행 검증을 구분한다.
3. **변경안 설명:** 현재 동작, 문제와 근거, 수정 파일과 이유, 변경 전후 코드 또는 diff, 확인 방법을 짧게 제시한다. 문서 작업이면 바꿀 규칙과 전후 설명을 제시한다.
4. **작은 범위 적용:** 기존 공개 API와 소유 관계를 먼저 활용한다. 생성·등록·구독을 추가하면 대응하는 실패·해제 경로도 같은 작업에 포함한다. 새 구조·패키지·전역 객체는 필요가 확인된 경우에만 추가한다.
5. **검증:** 변경 종류에 맞는 아래 기준을 사용한다. 기존 Console 기록을 확인한 뒤 이번 작업으로 생긴 문제를 구분한다. 로그를 지운 사실을 해결 근거로 삼지 않는다.
6. **마무리:** 이번 변경의 diff·문서 링크·UTF-8·필수 .meta를 확인한다. 아래 기준으로 즉시 갱신한 기능 README를 실제 변경과 대조하고 세션 기록에 요약한다. 적용 내용·확인 결과·미검증 사항을 구분해 보고한다.

작업 도중 다른 변경이 보이면 편집 직전에 대상 구간을 다시 읽고 해당 변경을 보존한다. 기록 갱신도 새로 추가된 다른 세션을 덮어쓰지 않는다. 설명·검토만 요청받은 경우에는 세션 기록을 포함한 파일 수정 없이 결과를 답한다.

## 기능 폴더의 현재 상태 갱신

1. **현재 구현·연결·진행 상태는 해당 기능 폴더의 README.md에 기록한다.** Docs/Rules와 루트 AGENTS.md에는 공통 기준과 문서 링크를 두고, “현재 미구현”, “다음에 연결” 같은 진행 상태를 쌓지 않는다.
2. 코드·씬·프리팹·Addressables 설정을 의미 있는 한 단계 변경하면 **그 단계에서 해당 README의 관련 문장도 즉시 수정한다.** 다음 작업이나 커밋까지 미루지 않는다. 수정 완료 보고 전에 문서 갱신이 끝나 있어야 한다.
3. 기존 설명을 현재 상태로 고친다. 이미 연결한 기능을 미구현 목록에 남기거나, 새 설명을 덧붙여 서로 반대되는 설명을 유지하지 않는다. 오래된 작업 내역은 README에 누적하지 않고 세션 기록에 남긴다.
4. 입력·호출자, 처리 순서, 상태·리소스 소유자, 출력·연결 결과, 반환·실패 처리, 검증 결과, 미완료 사항 중 **이번 변경으로 달라진 항목만** 갱신한다. 코드 반영과 실행 확인을 구분하고 미실행 검증은 그대로 적는다.
5. 변경이 여러 기능에 걸치면 영향을 받은 각 폴더의 README를 함께 갱신한다. 전체 시작 순서는 진입점 README, 개별 동작은 해당 기능 README에 두고 서로 링크한다. 동일한 상세 흐름을 여러 문서에 복사하지 않는다.
6. 해당 폴더에 README가 없으면 같은 기능을 설명하는 가장 가까운 상위 README를 사용한다. 독립된 기능이며 설명 위치가 없을 때만 그 기능 폴더에 README를 만든다. Assets 아래 새 문서는 .meta도 확인한다.
7. 세션 기록은 변경한 폴더·문서와 검증·남은 일을 요약한다. 세션 기록만 고치는 것으로 기능 README 갱신을 대신하지 않는다. 새 작업에서는 기능 README와 실제 파일을 우선 대조한다.

필요한 항목만 다음 형태로 적으며 기존 문서의 유용한 구조는 유지한다.

```markdown
## 현재 동작
입력·호출자 → 처리·소유자 → 출력·연결 결과
생성·활성화·갱신·반환 순서와 실패 시 정리 책임

## 확인과 남은 작업
- 확인한 내용: 실제 수행한 검증과 결과
- 미확인·미구현: 아직 실행하지 않은 검증 또는 연결하지 않은 기능
```

## 검증 방식

1. EditMode·PlayMode 테스트 코드와 테스트 어셈블리를 생성하지 않는다. 제거한 `91.Tests` 폴더를 다시 만들지 않는다.
2. 검증은 컴파일 확인, Unity Play에서의 실제 조작, 기능별 Cheat 창, Inspector와 Console 확인으로 수행한다. 실행하지 않은 검증을 통과로 적지 않는다.
3. Cheat 창은 Editor 전용으로 두고 실제 기능의 공개 API를 호출한다. 테스트를 위해 게임 로직을 복제하거나 실행 진입점에 임시 코드를 넣지 않는다.
4. 엔티티의 치트 전용 코드·필드·메뉴는 기존 로직 파일에 넣지 않고 같은 폴더의 `엔티티이름Cheat.cs`에 둔다. 예: PlayerCheat.cs, ZombieCheat.cs. 기존 클래스의 ContextMenu·직렬화 연결을 유지해야 하면 partial로 파일을 분리할 수 있으며, 치트를 위해 런타임 내부 상태를 공개하지 않는다. Editor용 치트는 파일 전체를 UNITY_EDITOR로 감싸 빌드에서 제외한다. 공용 Cheat 창은 기존 90.Editor에 둔다.

| 변경 종류 | 확인할 내용 |
| --- | --- |
| 문서·규칙 | 실제 코드와 설명 일치, 상대 링크, 이전 지시와 충돌, diff 공백 검사 |
| C# 코드 | Unity 컴파일·Console, 관련 Cheat 또는 실제 기능 조작 |
| 씬·프리팹 연결 | Inspector 참조·소속 씬·활성화 순서, 실제 생성과 해제 |
| Addressables 등록 | 그룹·주소·GUID·중복 여부. 등록 확인과 실제 로드·반환, 번들 빌드는 별개로 보고 |
| 비동기 생성·반환 | 정상 완료, 중복 호출, 준비 중 반환, 부분 실패 시 소유 요청 정리 중 변경에 해당하는 경로 |

게임 실행의 기본 확인은 Start 씬에서 시작한다. 구체적인 카메라·맵·플레이어·HUD 확인 순서는 [진입점 안내](../../Assets/_Project/01.Boot/README.md)를 따른다. 도구 연결이나 실행 환경이 없으면 정적 확인 결과와 실행하지 못한 항목을 명시한다.

## 파일과 검증

1. 모든 파일을 UTF-8로 읽고 저장한다. 한글이 포함된 기존 파일은 필요한 부분만 수정하고, 요청과 무관한 전체 재작성·줄바꿈 변경을 하지 않는다.
2. 이번 변경에 맞는 검증을 선택한다. 문서만 바꿨다면 경로·링크·내용을 확인하고 불필요한 게임 빌드나 테스트를 실행하지 않는다.
3. 컴파일 통과와 실제 게임 실행 성공을 구분한다. 실패·보류·미실행 항목을 결과에 명시한다.
4. 코드 구조·공개 API·폴더 역할을 바꾸면 관련 README도 갱신한다. 계획과 실제 구현 완료 상태를 구분한다.
5. Unity MCP 등 도구는 실제 제공되는 기능을 확인해 사용한다. 도구 이름이나 기능을 추측하지 않는다.

## 실습을 위한 답변

1. 답변은 사용자가 직접 따라 하며 익힐 수 있는 실습 형태로 작성한다.
2. 입력 → 처리 → 출력 순서로 현재 동작을 먼저 설명한다.
3. 한 번에 큰 완성 코드를 제시하기보다 작은 단계로 나누어 설명한다.
4. 각 단계에는 수정할 위치, 작성할 코드, 코드의 역할과 Unity에서 확인하는 방법을 포함한다.
5. 오류가 발생할 수 있는 지점과 확인해야 할 Inspector 설정도 함께 설명한다.
6. 사용자가 완성 코드나 즉시 적용을 요청하지 않았다면 먼저 생각할 부분과 실습 순서를 안내한다.

## 세션 기록

1. 시작할 때 [Docs/Work/last-session.md](../Work/last-session.md)를 읽고 실제 파일·Git 상태와 대조한다.
2. 세션을 마무리할 때 작업 내용·진행 상태·다음 할 일·수정 파일을 항목당 한 문장으로 간략하게 기록한다. 상세 구현 과정·검증 수치·전체 파일 목록은 반복하지 않고 필요한 기능 문서를 연결한다. 완료한 일과 제안만 한 일을 구분한다. 단, 커밋·푸시 작업만 수행할 때는 마지막 작업 기록을 추가하거나 갱신하지 않는다.
3. 새 기록을 맨 위에 두고 기존 마지막 기록은 이전 작업으로 남긴다. 기록이 길어지면 오래된 항목을 같은 폴더의 날짜별 문서로 옮긴다.
4. 검증 결과와 미검증 범위는 진행 상태에 적는다. 사용자 결정·보류 조건은 다음 할 일에 남긴다.
5. 세션 기록은 문서로 직접 갱신한다. 별도 자동 저장 프로그램이나 개인 훅이 설치되어 있다고 가정하지 않는다.

형식:

```markdown
## 마지막 작업 (YYYY-MM-DD HH:mm)
- 작업 내용:
- 진행 상태:
- 다음 할 일:
- 수정한 파일:
```
