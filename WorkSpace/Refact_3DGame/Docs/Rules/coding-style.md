# 코드 작성 규칙

## 책임과 크기

1. 유지보수성, 가독성, 변경 용이성, 책임 분리와 SOLID 원칙을 기준으로 검토한다.
2. 클래스·함수를 무조건 잘게 나누지 않는다. 현재 규모에서 함께 둘 책임과 변경 이유가 달라 분리할 책임을 구분한다.
3. 함께 둔 책임도 의존성, 호출 순서, 변경 위치가 보이게 작성한다.
4. 반복되는 중복이나 별도 변경 이유가 있을 때 분리한다. 필요가 확인되지 않은 패턴·추상화·util/helper/common 계층을 추가하지 않는다.
5. 외부 API·파일·네트워크·데이터베이스·유료 서비스 호출은 핵심 게임 규칙과 구분하고 교체 지점을 명확히 한다.
6. 기존 기능의 이름공간·스타일을 우선하며 새 규칙을 이유로 관계없는 코드를 일괄 수정하지 않는다.

## 이름과 주석

1. 식별자는 영어, 설명과 주석은 한국어를 기본으로 한다. 역할이 바로 드러나는 쉬운 단어를 사용한다.
2. 클래스·공개 멤버는 PascalCase, 필드·매개변수·지역 변수는 camelCase를 기본으로 한다. 기존 코드의 일관성을 우선한다.
3. 행동은 LoadMap, Release처럼 대상과 동작이 드러나게 쓴다. 필요 이상으로 Manager, Data, Helper 같은 넓은 이름을 붙이지 않는다.
4. Container는 무엇을 보관하고 누가 생성·반환하는지 설명할 수 있을 때 사용한다. 단일 객체라는 이유만으로 별도 컨테이너를 만들지 않는다.
5. 접근 제한자를 명시하고, 외부에서 임의 변경하면 안 되는 값은 필드 대신 조회용 프로퍼티·메서드로 제공한다.
6. 주석은 이름의 반복보다 이유·소유권·호출 조건을 설명한다. 공개 API의 반환값이나 완료 시점이 헷갈릴 때 XML 문서 주석으로 계약을 적는다.

## 상수와 설정

1. 여러 기능이 같은 의미로 사용하는 고정 값은 02.Core/Constant에서 관리한다. 현재 ConstantValid partial 구조를 따른다.
2. 기능 내부에서만 쓰는 상수는 그 기능에 둔다. 값이 같아도 변경 이유가 다르면 억지로 합치지 않는다.
3. Inspector에서 조절할 값과 게임 진행 중 바뀌는 상태를 const로 바꾸지 않는다.
4. Animator 해시처럼 실행 시 계산되는 고정 값은 필요에 따라 static readonly로 한 번 계산한다.
5. 상수 변경만으로 씬·프리팹의 직렬화 값이나 Addressables 등록 값이 갱신되지는 않는다. 사용처와 설정을 함께 확인한다.

## Unity C#과 GC

1. Unity C# 코드는 런타임 GC 할당을 고려하여 작성한다.
2. `Update`, `FixedUpdate`, `LateUpdate`처럼 자주 호출되는 구간에서는 불필요한 객체 생성, 문자열 생성, LINQ, 클로저와 반복적인 `GetComponent` 호출을 피한다.
3. 자주 사용하는 컴포넌트와 값을 캐시하되, 캐시가 필요한 이유와 값이 갱신되는 시점을 명확히 한다.
4. 모든 할당을 무조건 제거하지 않는다. 호출 빈도와 실제 성능 영향을 근거로 필요한 최적화만 적용한다.
5. GC 최적화 때문에 코드의 역할과 동작 흐름이 지나치게 복잡해지지 않도록 한다.

## 이름공간

1. 프로젝트 코드는 역할에 맞는 이름공간(`namespace`)에 배치한다.
2. 이름공간은 프로젝트명 → 기능 영역 → 세부 역할 순서로 구성한다.
3. 기존 이름공간이 있으면 해당 구조와 대소문자를 우선하여 따른다.
4. 임의로 새로운 최상위 이름공간을 만들지 않는다.
5. 폴더 구조와 이름공간이 가능하면 서로 대응하도록 구성한다.

## 생명주기 커스터마이징

1. Unity 생명주기에 직접 묶일 필요가 없는 로직은 일반 C# 클래스로 구현하여 생명주기를 호출자가 제어할 수 있게 한다.
2. 생성, 활성화, 갱신, 비활성화, 해제가 필요한 객체는 역할에 맞게 `Create`, `Enable`, `Update`, `Disable`, `Destroy` 또는 `Dispose`처럼 명확한 호출 지점을 제공한다.
3. 커스텀 생명주기의 호출 순서와 호출 책임을 한곳에서 확인할 수 있게 구성한다.
4. `MonoBehaviour`는 Inspector 연결, Unity 이벤트, 코루틴, 물리 충돌처럼 Unity 기능이 필요한 경계 역할을 우선 담당한다.
5. Unity가 직접 관리해야 하는 컴포넌트까지 무조건 일반 C# 클래스로 분리하지 않는다.
6. 커스텀 생명주기를 추가할 때는 중복 호출, 호출 누락과 해제되지 않은 이벤트 구독이 발생하지 않도록 방어한다.

## 참조와 오류 처리

1. 필요한 객체는 생성자·초기화 메서드·Inspector 참조로 전달한다. 반복 검색으로 의존성을 숨기지 않는다.
2. 생성 → 연결 → 활성화 → 갱신 → 비활성화 → 해제 중 필요한 단계만 둔다. 현재 Update/Tick 명칭은 해당 기능의 기존 API를 따른다.
3. 이벤트 구독과 해제, Addressables 로딩과 반환을 짝지어 관리한다.
4. 잘못된 입력, 중복 호출, 비동기 작업 중 재요청과 실패 후 상태를 확인한다. 성공으로 숨기거나 빈 catch로 오류를 삼키지 않는다.
5. 실행 순서는 연결을 요청받은 단계에서 구현한다. 틀 정리 요청에 자동 생성·게임 실행까지 붙이지 않는다.
