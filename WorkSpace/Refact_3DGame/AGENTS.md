# 프로젝트 에이전트 규칙

## 코드 수정

1. 사용자가 명확하게 “수정해”, “적용해”, “진행해”라고 요청한 경우에만 실제 코드를 수정한다.
2. 코드 수정 전에는 현재 동작 순서, 문제점, 수정 대상, 수정 이유, 예상 변경 범위와 변경 전후 코드를 먼저 설명한다.
3. 분석, 검토, 설명 요청에서는 파일을 수정하지 않는다.
4. 기존 동작을 유지하면서 작은 단위로 점진적으로 수정한다.

## Unity C#과 GC

1. Unity C# 코드는 런타임 GC 할당을 고려하여 작성한다.
2. `Update`, `FixedUpdate`, `LateUpdate`처럼 자주 호출되는 구간에서는 불필요한 객체 생성, 문자열 생성, LINQ, 클로저와 반복적인 `GetComponent` 호출을 피한다.
3. 자주 사용하는 컴포넌트와 값을 캐시하되, 캐시가 필요한 이유와 값이 갱신되는 시점을 명확히 한다.
4. 모든 할당을 무조건 제거하지 않는다. 호출 빈도와 실제 성능 영향을 근거로 필요한 최적화만 적용한다.
5. GC 최적화 때문에 코드의 역할과 동작 흐름이 지나치게 복잡해지지 않도록 한다.

## 이름공간

1. 프로젝트 코드는 역할에 맞는 이름공간(`namespace`)에 배치한다.
2. 이름공간은 프로젝트명 → 기능 영역 → 세부 역할 순서로 구성한다.
3. 기존 이름공간이 있으면 해당 구조와 대소문자를 우선하여 따른다.
4. 임의로 새로운 최상위 이름공간을 만들지 않는다.
5. 폴더 구조와 이름공간이 가능하면 서로 대응하도록 구성한다.

## 생명주기 커스터마이징

1. Unity 생명주기에 직접 묶일 필요가 없는 로직은 일반 C# 클래스로 구현하여 생명주기를 호출자가 제어할 수 있게 한다.
2. 생성, 활성화, 갱신, 비활성화, 해제가 필요한 객체는 역할에 맞게 `Create`, `Enable`, `Update`, `Disable`, `Destroy` 또는 `Dispose`처럼 명확한 호출 지점을 제공한다.
3. 커스텀 생명주기의 호출 순서와 호출 책임을 한곳에서 확인할 수 있게 구성한다.
4. `MonoBehaviour`는 Inspector 연결, Unity 이벤트, 코루틴, 물리 충돌처럼 Unity 기능이 필요한 경계 역할을 우선 담당한다.
5. Unity가 직접 관리해야 하는 컴포넌트까지 무조건 일반 C# 클래스로 분리하지 않는다.
6. 커스텀 생명주기를 추가할 때는 중복 호출, 호출 누락과 해제되지 않은 이벤트 구독이 발생하지 않도록 방어한다.

## 실습을 위한 답변

1. 답변은 사용자가 직접 따라 하며 익힐 수 있는 실습 형태로 작성한다.
2. 입력 → 처리 → 출력 순서로 현재 동작을 먼저 설명한다.
3. 한 번에 큰 완성 코드를 제시하기보다 작은 단계로 나누어 설명한다.
4. 각 단계에는 수정할 위치, 작성할 코드, 코드의 역할과 Unity에서 확인하는 방법을 포함한다.
5. 오류가 발생할 수 있는 지점과 확인해야 할 Inspector 설정도 함께 설명한다.
6. 사용자가 완성 코드나 즉시 적용을 요청하지 않았다면 먼저 생각할 부분과 실습 순서를 안내한다.
