# v3 사용 기술과 개선 기록

분석 기준: v3 / e7a73261 · 분석일: 2026-09-10

코드·커밋·개발 문서에서 확인한 사실만 정리했다. 선택 이유와 원인·결과는 추정하지 않았다. 기록이 없으면 “확인할 근거 없음”으로 표시했다. 코드 구현, 당시 문서의 실행 결과, 이번 분석의 확인 범위는 구분한다. 이번에는 Unity 실행·빌드·테스트·성능 측정을 하지 않았다.

## 프로젝트와 동작 흐름

Unity 6으로 갱신하고 소울라이크 전투, 월드 객체 생명주기, 인벤토리·지역 씬·미니맵을 구현한 브랜치다.

PlayerInputReader 입력 보관 → WorldObjectManager의 Tick → PlayerWorldUnit → 시점·행동 상태 → 이동·공격 판정 → 체력·스태미나·피격 결과 → HUD 이벤트 순서다. 지역 씬 로딩은 별도 컨테이너가 요청받아 처리한다. [S11·S12·S13·S17·S19·S21]

로컬 v3만 가진 커밋은 저장된 origin/v3 참조보다 9개 많다. 외부 에셋 추가와 MCP 설정이며, 원격 서버의 실시간 상태를 조회한 결과는 아니다.

## v3 안의 개선 내용, 이유와 결과

### 1. 카메라가 플레이어 회전을 상속하는 문제

- 사용 기술: Cinemachine, Transform 계층 분리.
- 기록된 문제·이유: 카메라가 플레이어 이동 회전에 함께 끌려가지 않도록 계층을 분리했다고 개발 기록에 명시되어 있다.
- 변경: `CameraGroup`을 `PlayerRoot` 자식에서 씬 루트로 이동하고, 플레이어의 `CameraTarget`은 Follow·LookAt 대상으로 사용했다.
- 흐름: 마우스 Look 입력 → Cinemachine 카메라 → CameraTarget 추적 → 화면 출력.
- 기록된 결과: 2026-07-27 기록에 카메라 계층 확인, 스크립트 컴파일 성공, 콘솔 Error·Exception 없음이 적혀 있다. 현재 버전을 다시 실행한 결과는 아니다.
- 근거: S10·S11.

### 2. 상태 분리와 입력 예약

- 사용 기술: 상태머신, 짧은 입력 버퍼.
- 기록된 이유: 이동·방어·구르기를 한 Update의 조건문으로 처리하지 않고, 상태 전환 위치를 한곳에 모으려는 목적이 기록되어 있다.
- 변경: 시점은 자유 시점·락온, 행동은 이동·방어·구르기·공격으로 나뉜다. `PlayerActionInputBuffer`는 마지막 공격 또는 구르기 하나를 보관한다.
- 규칙: 같은 프레임에는 구르기 우선, 새 입력은 이전 예약 교체, 보관 시간이 설정값을 초과하면 삭제, 소비 후 초기화.
- 결과: 입력 우선순위·교체·만료를 검사하는 테스트 코드가 있다. 입력 누락률이나 조작 만족도 개선 측정값은 확인할 근거 없음.
- 근거: S11·S12, `0ea51b08`.

### 3. 공격 중 구르기와 방어 준비 시간 조정

- 사용 기술: Animator 전환 설정, 방어 준비 시간.
- 기록된 변경: `67bd36e8`은 공격 중 구르기 전환을 즉시 시작하고 방어 준비 시간을 단축했다고 명시한다.
- 확인한 diff: `PlayerController`의 당시 기본 `guardRaiseDuration`을 `0.1f`에서 `0.05f`로 바꾸고 Animator Controller와 프리팹을 함께 변경했다.
- 이유: 변경 의도는 커밋에 적혀 있지만, 기존 지연의 측정값·원인 분석 자료는 확인할 근거 없음.
- 결과: 설정 변경은 확인했다. 실제 조작 지연 감소량과 현재 모든 공격에서의 동작 검증 결과는 확인할 근거 없음.
- 근거: `67bd36e8`. 해당 수치는 당시 diff이며 현재 모든 설정값을 뜻하지 않는다.

### 4. 월드 객체 호출 순서와 풀 관리

- 사용 기술: 일반 C# 생명주기, List·HashSet, 대기 작업 목록, Unity ObjectPool.
- 기록된 이유: 생성·활성화·갱신·비활성화·정리 순서와 중복 호출을 관리하도록 구성했다.
- 변경 흐름: Controller가 Unity 참조 연결 → Manager 등록 → RuntimeObject 활성화·Tick → 비활성화 → 최종 Dispose.
- 코드로 확인한 방어: 생성 전 Enable 거부, 중복 Create·Disable·Dispose 방지, Tick 중 들어온 등록·반환 요청을 순회 종료 후 처리.
- 결과: View와 RuntimeObject를 함께 재사용하는 풀, 예열, 사용 중 객체와 보관 객체 정리를 확인했다. 현재 플레이어는 풀 대상이 아니다.
- 범위: 현재 `ItemSpawnManager`도 `Instantiate`를 직접 쓴다. 모든 월드 객체를 풀링했다는 설명은 근거와 다르다.
- 근거: S11·S13·S20.

### 5. 검의 현재 위치와 프레임 사이 궤적 검사

- 사용 기술: `OverlapCapsuleNonAlloc`, `SphereCastNonAlloc`, 고정 배열, HashSet.
- 확인한 처리 대상: 공격 구간 동안 현재 검 형상과 프레임 사이 궤적을 검사한다는 코드 설명이 있다. 과거 타격 누락의 실제 재현 기록은 확인할 근거 없음.
- 흐름: 공격 구간 열기 → 현재 Capsule 검사 → 검 시작·중간·끝점의 이전 위치부터 현재 위치까지 SphereCast → 대상별 피해 요청 → 구간 닫기.
- 중복 처리: 한 공격 구간에서 `HashSet<IEnemyDamageReceiver>`에 이미 추가된 대상은 다시 처리하지 않는다.
- 결과와 한계: 검출 버퍼는 각각 32칸, HashSet 초기 용량은 16이다. 이 구현만으로 모든 밀집 상황의 누락 방지나 공격 전체 `GC Alloc 0 B`를 보장할 수는 없다. 해당 실측 근거는 없음.
- 근거: S14.

### 6. 공격 전진 거리와 회전 제한

- 사용 기술: `AttackTargetCorrection`, 이동 곡선, CharacterController.
- 기록된 목표: 공격 시작 시 대상·거리·방향을 저장하고 제한 회전과 곡선 전진을 적용한다.
- 역할 분리: 보정 계산기는 계획 거리·회전 제한을 계산하고, 공격 상태는 시작·유효성·구간을 관리하며, Movement가 실제 이동을 적용한다.
- 2026-08-22 기록된 결과: 관련 테스트 39 통과·0 실패. 전체 EditMode 124 통과·2 실패. 30·60·120 FPS 계산 조건에서 요청 누적 거리가 계획 거리와 0.0001m 이내로 일치했다.
- 미확인: 실제 CharacterController 충돌 결과, 좁은 공간 PlayMode, Profiler 실측. 따라서 실제 이동이 모든 프레임 조건에서 검증되었다고 표현하지 않는다.
- 근거: S15. 위 수치는 당시 개발 문서의 기록이며 이번 분석에서 재실행하지 않았다.

### 7. NightShade 연속 공격 연결 보정

- 사용 기술: 애니메이션 진행률, 콤보 상태·설정, 에셋 테스트.
- 변경 전 코드: 공격 종료 판단에 공통으로 `normalizedTime >= 1f`를 사용했다.
- 변경: `232a39df`에서 콤보 1타는 별도 종료 진행률을 사용하게 하고, 2타 대기 중 Idle 재생을 조건부로 막았다. 설정 생성자에 전달하는 두 인자의 순서도 수정했다.
- 기록된 테스트 변경: 테스트 시나리오가 1타 진행률 `0.4` 종료와 `0.15초` 대기를 검사하도록 변경됐다.
- 결과: 종료·대기·전달 인자 수정은 diff로 확인했다. 수정 당시의 체감 증상·정확한 원인 확정·실행 성공 자료는 확인할 근거 없음.
- 범위: 이 사례는 당시 구현에 대한 기록이다. 현재 NightShade는 Attack Action 구조를 사용한다.
- 근거: `232a39df`, S16.

### 8. NightShade 공격 선택과 실행 분리

- 사용 기술: 점수 기반 행동 선택, 실행기, 교체 가능한 난수 제공자.
- 흐름: 대상 상태·전투 기억 → 실행 가능 후보 필터 → 기본 점수·거리 적합도·반복 감점·난수 보정 → 최고 점수 행동 선택 → 실행기가 Enter·Update·Exit 호출.
- 확인한 책임: Selector는 선택, Action은 개별 행동, Runner는 실행 순서를 담당한다. 난수는 `INightShadeSwordRandomProvider`로 전달받는다.
- 이유: 역할은 코드에 명시되어 있다. 이 방식이 Behavior Tree나 다른 방식보다 적합하다고 판단한 비교 기록은 확인할 근거 없음.
- 결과: 선택·실행·반복 할당을 검사하는 테스트 코드가 있다. AI 다양성 증가율이나 난이도 개선 실험값은 확인할 근거 없음.
- 근거: S16·S24.

### 9. 좀비 경로 안내와 실제 이동 분리

- 사용 기술: NavMeshAgent, `IEnemyPathGuide`, CharacterController.
- 흐름: 목표 위치 → NavMesh 목적지·경로 계산 → 수평 이동 방향 → ZombieMovement의 실제 이동.
- 코드로 확인한 역할: Agent의 `updatePosition`, `updateRotation`을 끄고 실제 위치를 `nextPosition`에 맞춘다.
- 갱신 규칙: 첫 목적지 요청, 갱신 시간 만료 또는 목표가 0.5m 이상 이동했을 때 목적지를 갱신한다. 갱신 간격 상수는 0.2초다.
- 결과: 경로 안내 인터페이스와 유효하지 않은 경로·Agent 상태에서의 중단 처리가 있다. 과거 경로 충돌 문제나 해결 후 이동 성공률은 확인할 근거 없음.
- 근거: S18, `98acce94`.

### 10. 피해·가드·피격 반응과 타격 정지

- 사용 기술: 요청·결과 타입, 체력·스태미나·경직 계산, Animator 속도 제어.
- 플레이어 처리: 무효·사망 확인 → 구르기 무적 → 가드 가능 여부·스태미나 → 일반 체력 피해 → 피격 반응.
- 확인한 규칙: 방어 가능한 공격에서 현재 스태미나가 양수인 가드 비용과 같으면 GuardBroken이다. `HitReactionPlayback`은 더 약한 반응의 재시작을 막고 SmallHit 재시작에 0.18초 제한을 둔다.
- 타격 정지: `CombatHitStop`은 한 유닛의 Animator 속도를 보관하고 0으로 바꾸며, 해당 유닛의 Tick을 일시 중단한다. 중복 요청은 남은 시간과 새 시간 중 큰 값을 사용하고 Reset에서 속도를 복구한다.
- 이유·결과: 코드에 피격·가드 연출과 약한 반응 재시작 방지 목적이 명시되어 있다. 관련 규칙 테스트는 있으나 타격감 개선에 대한 사용자 평가 자료는 확인할 근거 없음.
- 근거: S17.

### 11. v2 이벤트 UI와 v3 구독 정리

- 사용 기술: C# 이벤트, UI Toolkit, UGUI.
- 기록된 목적: `v2` README는 반복 수치 확인 대신 이벤트로 UI 연산 낭비를 줄인다고 설명한다.
- 흐름: 체력·스태미나·가방 변경 → 이벤트 → HUD Controller → 화면 값 갱신.
- 확인한 차이: `v2 PlayerGUIController`는 `OnStatChanged`에 등록한 핸들러와 람다를 `OnDestroy`에서 해제하지 않는다. `v3 CombatHudController`에는 유닛 해제·비활성화 시 구독 정리 경로가 있다.
- 결과: 두 구현의 구독·해제 차이는 확인했다. 이를 동일 버그의 연속 수정이라고 연결할 기록, 메모리 누수 발생·해결 측정값은 확인할 근거 없음.
- 근거: S19.

### 12. 가방이 찼을 때 아이템 교환

- 사용 기술: 일반 C# 인벤토리, ScriptableObject 아이템, NUnit.
- 처리 조건: 교환 비용 아이템의 마지막 1개를 사용해 빈 칸이 생기는 경우를 코드와 테스트가 다룬다. 실제 서비스 장애 기록은 확인할 근거 없음.
- 흐름: 교환 가능 여부 확인 → 비용 차감 → 보상 추가 → Changed·ItemExchanged 알림.
- 확인한 결과: 가방이 꽉 차도 비용 아이템으로 비워지는 칸을 사용할 수 있다. 교환 실패 시 기존 가방 보존, 성공 시 Changed 한 번 발생을 검사하는 테스트 코드가 있다.
- 이유: 이 규칙을 선택한 기획 이유와 플레이 검증 결과는 확인할 근거 없음.
- 근거: S20.

### 13. 지역 씬·조명·리소스 관리

- 사용 기술: Additive 씬 로딩, 코루틴, 씬 이벤트, 라이트맵 정리.
- 문서상 역할: Common은 상주 객체, Ground·Underground는 해당 지역 배치와 참조를 소유한다. 공유 원본 에셋은 복제하지 않는다.
- 흐름: Load 요청·중복 검사 → `LoadSceneAsync(Additive)` → 활성 씬·Setup&Lights 선택. Unload 요청 → 씬 해제 → 미사용 라이트맵 정리 → `UnloadUnusedAssets` 완료 대기.
- 확인한 방어: 처리 중 추가 작업 거부, 로딩 중 비활성화 대응, 이전 Time.timeScale 복구가 있다.
- 결과와 한계: 컨테이너는 씬 정보만 보관하며 퀘스트·가방·미니맵을 직접 제어하지 않는다. 다른 씬이나 정적 참조가 에셋을 잡고 있으면 남을 수 있다고 문서에 적혀 있다. 실제 메모리 감소량은 확인할 근거 없음.
- 근거: S21.

### 14. 층별 미니맵

- 사용 기술: 전용 카메라·마커, `MinimapFloor`, 씬 로딩 이벤트.
- 흐름: 씬 로드·해제 시 층 목록 갱신 → 플레이어 높이로 층 선택 → LateUpdate에서 카메라·마커 위치 갱신.
- 확인한 규칙: 현재 층에는 경계 여유값을 적용한다. `MinimapCameraController`의 기본값은 0.5m다. 범위에 맞는 층이 없으면 가장 가까운 층을 선택한다.
- 결과: 층 선택과 씬 목록 갱신이 씬 컨테이너와 분리되어 있다. 경계 떨림이 실제 발생했고 해결됐다는 기록, 렌더 비용 측정값은 확인할 근거 없음.
- 근거: S22.

### 15. 테스트로 확인한 범위와 남은 검증

- 사용 기술: NUnit, EditMode 테스트, 어셈블리 정의, 테스트 대역.
