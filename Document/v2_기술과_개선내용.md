# v2 사용 기술과 개선 기록

분석 기준: v2 / 540827f4 · 분석일: 2026-09-10

코드·커밋·개발 문서에서 확인한 사실만 정리했다. 선택 이유와 원인·결과는 추정하지 않았다. 기록이 없으면 “확인할 근거 없음”으로 표시했다. 코드 구현, 당시 문서의 실행 결과, 이번 분석의 확인 범위는 구분한다. 이번에는 Unity 실행·빌드·테스트·성능 측정을 하지 않았다.

## 프로젝트와 동작 흐름

초기 RPG를 리팩토링한 브랜치다. main의 7512f398과 v2 끝을 비교하면 파일 내용 차이는 없다.

입력·적 탐지 → 현재 상태 Tick → 공격 데이터·무기 충돌 → 피해·스탯 변경 → UI 이벤트 순서다. 적은 사망 보상 → 사망 연출 완료 → 풀 반환 → 재사용으로 처리한다. 저장은 PlayerSavedData → SaveData → JSON 파일 순서다. [S06·S08·S09]

## v1 대비 개선 내용, 이유와 결과

### 1. v1 적 Behavior Tree → v2 적 상태머신

- 사용 기술: Behavior Tree, State 패턴.
- 기존 흐름: `Zombie1.Update` → 탐지·거리 갱신 → `behaviorTree.Evaluate()` → 이동·공격.
- 문제와 이유: `v2` README에 애니메이션 타이밍과 상태 전이를 명확히 관리하려는 이유가 기록되어 있다. 특정 Behavior Tree 결함의 재현 자료는 확인할 근거 없음.
- 변경: `EnemyStateMachine`이 기존 상태 `Exit` → 새 상태 지정 → `Enter`를 수행하고, 매 프레임 현재 상태만 `Tick`한다.
- 결과: 적의 대기·이동·공격·피격·사망 클래스 분리를 코드로 확인했다. FSM 전환만의 FPS 개선량은 확인할 근거 없음.
- 근거: S02·S06, `v2:README.md`.

### 2. v2 캐릭터 설정과 공격 데이터 분리

- 사용 기술: ScriptableObject, 상속, 공격 데이터.
- 기록된 이유: `66e5cbbf`에 공통 스탯을 부모에 두고 Enemy·Player와 적 종류별 특성으로 확장한다고 적혀 있다.
- 변경: `CharacterStatPreset`이 체력·공격력·방어력을 제공한다. `AttackData`가 애니메이션 이름·사거리·타격별 무기 번호·피해를 보관한다.
- 흐름: 설정 에셋 → 캐릭터 초기화·현재 공격 데이터 조회 → 실제 스탯·타격 피해 반영.
- 결과: 수치·기존 공격 데이터의 편집 지점은 확인된다. 새로운 행동 종류까지 코드 수정 없이 추가된다는 근거, 메모리 감소 측정값은 확인할 근거 없음.
- 근거: S07·S06, `66e5cbbf`.

### 3. v1 → v2 피해 공식 변경

- 사용 기술: 공통 피해 계산 함수, 비율식 방어 계산.
- 기존 코드: `v1`은 `max(공격력 × max(1 - 방어력 × 0.01, 0.2), 1)`을 사용한다. 이미 최소 피해를 보장한다.
- 변경 코드: `v2`는 `max(공격력 × 200 / (200 + 방어력), 1)`을 사용한다.
- 기록된 이유: `v2` README에는 높은 방어력에서 피해가 0이 되는 현상 방지와 밸런스를 이유로 적었다. 다만 README의 기존 식 설명과 상수 `100`은 분석한 브랜치 끝의 코드와 다르다.
- 결과: 실제 공식과 최소 피해 `1`은 확인했다. 이 변경으로 밸런스가 개선되었다는 플레이 실험 자료는 확인할 근거 없음.
- 근거: S05, `v2:README.md`.

### 4. v2 적 생성·사망·재사용

- 사용 기술: `Queue<Enemy>`, 이벤트, 코루틴.
- 기존 코드: `v1`의 `EnemySpawner`는 재소환 때 `Instantiate`를 호출한다.
- 기록된 이유: `v2` README에 반복 생성·파괴와 GC 부담 감소 목적이 적혀 있다.
- 변경 흐름: 소환 위치 수만큼 미리 생성 → Queue에서 꺼내 활성화·초기화 → 사망 시 처치 수·경험치 처리 → 사망 연출 종료 후 비활성화·Queue 반환 → 지연 후 재사용.
- 결과: 적 재사용 경로와 사망 보상·연출 완료 이벤트 분리를 확인했다. 풀링만으로 얻은 CPU·GC·FPS 개선량은 확인할 근거 없음.
- 범위: 이 코드만으로 모든 이펙트도 풀링한다고 설명할 수 없다.
- 근거: S08.

### 5. v2 저장된 처치 수와 이어하기

- 사용 기술: JSON, 저장 데이터 객체, Build Index.
- 변경 흐름: JSON 읽기 → `PlayerSavedData` 복원 → 저장된 씬 번호로 이동 → 플레이어 준비 대기 → 저장된 `killCount`로 스포너·UI 초기화.
- 코드로 확인한 처리: `SpawnController`는 저장된 처치 수가 목표 이상이면 포탈을 활성화한다. `LobbyUI`는 파일 존재와 `savedIndex > 3`으로 이어하기 버튼 활성 여부를 정한다.
- 기록된 이유: `v2` README에는 유효한 전투 스테이지 이어하기와 저장 보존 목적이 있다.
- 결과와 한계: 복원 경로는 확인했다. `LobbyUI`의 조건만으로 씬 번호 상한·빌드 등록 유효성까지 검증한다고 할 수 없다. JSON 손상·파일 쓰기 실패 복구는 확인한 `SaveSystem`에 없다.
- 근거: S09.

### 6. 이벤트로 플레이어 UI 갱신

- 사용 기술: C# 이벤트, UGUI Slider, TextMesh Pro.
- 변경 내용: PlayerGUIController가 체력·스태미나·경험치·레벨·스탯 변경 이벤트를 구독한다.
- 기록된 이유: README에는 매 프레임 수치 확인에 따른 UI 연산 낭비를 줄이기 위해서라고 적혀 있다.
- 흐름: 플레이어 값 변경 → 이벤트 → 해당 Slider·텍스트 갱신. 최초 연결 시에는 전체 UI를 한 번 갱신한다.
- 확인된 결과: 이벤트 기반 호출 구조를 확인했다. UI CPU 시간 감소량은 확인할 근거 없음.
- 남은 코드: OnStatChanged에 등록한 핸들러·람다가 OnDestroy에서 해제되지 않는다. 실제 누수 발생 여부는 실행 측정하지 않았다.
- 근거: S19, v2:README.md.

### 7. 캐릭터 애니메이션 정리

- 사용 기술: Animator·Animation Clip.
- 기록된 문제와 변경: 66e5cbbf에는 작동하지 않던 애니메이션을 다시 작동하도록 정리했다고 적혀 있다.
- 수정 이유: 작동하지 않는 애니메이션의 복구 목적은 기록으로 확인된다. 원인별 분석·구체적인 수정 선택 이유는 확인할 근거 없음.
- 결과: 정상화했다는 당시 커밋 기록이다. 이번에 애니메이션을 실행해 확인한 결과는 아니다.
- 근거: 66e5cbbf.
