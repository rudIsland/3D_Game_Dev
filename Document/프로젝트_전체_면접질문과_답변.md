## 프로젝트 소개와 버전

**질문 01. 이 프로젝트를 짧게 소개해 주세요.**

**답변:** 초기 3D TPS RPG에서 시작해 적 AI·데이터·풀링을 리팩토링했고, v3에는 소울라이크 전투와 지역·아이템 기능을 구현했습니다. [S02·S06·S11·S21]


**질문 02. v1, v2, v3의 핵심 차이는 무엇인가요?**

**답변:** v1은 초기 RPG, v2는 적 FSM·SO·풀링 중심 리팩토링, v3는 전투 상태·월드 생명주기·지역 씬 구조의 확장입니다. [v1](v1_기술과_개선내용.md) · [v2](v2_기술과_개선내용.md) · [v3](v3_기술과_개선내용.md)


**질문 03. main과 v2는 다른 구현인가요?**

**답변:** 커밋 이력은 다르지만, 분석한 두 브랜치 끝의 파일 내용은 같습니다. `git diff main v2`에 차이가 없습니다.


**질문 04. 어떤 Unity 버전을 사용했나요?**

**답변:** v1·v2는 2022.3.44f1, v3는 6000.3.9f1입니다. ProjectVersion.txt 기준입니다. [S01]


## AI와 상태 처리

**질문 05. 처음 적 AI에는 무엇을 사용했나요?**

**답변:** Behavior Tree입니다. Selector·Sequence·Action 노드로 탐지·이동·공격을 구성했고, README에는 적 행동 다양성을 위한 학습이라고 기록했습니다. [S02]


**질문 06. 적 AI를 FSM으로 바꾼 이유는 무엇인가요?**

**답변:** 기록된 이유는 애니메이션 타이밍과 상태 전이를 명확히 관리하기 위해서입니다. 적의 상태를 클래스로 나누었습니다. [S06]


**질문 07. 상태 전환은 어떤 순서로 실행되나요?**

**답변:** 기존 상태 Exit → 새 상태 지정 → Enter 순서입니다. 이후 현재 상태의 Tick을 호출합니다. [S06]


**질문 08. v3 플레이어는 시점과 행동을 어떻게 관리하나요?**

**답변:** 자유 시점·락온 상태와 이동·공격·방어·구르기 행동 상태를 분리합니다. 피격·사망 전환도 별도로 처리합니다. [S12]


**질문 09. 입력 버퍼에는 무엇을 보관하나요?**

**답변:** 마지막 공격 또는 구르기 하나를 보관합니다. 새 입력은 기존 예약을 교체하고, 시간이 초과되거나 소비되면 지웁니다. [S12]


**질문 10. 공격과 구르기를 동시에 누르면 어떻게 되나요?**

**답변:** 같은 프레임에서는 구르기를 우선 예약합니다. 이 규칙을 검사하는 테스트가 있습니다. [S12]


## 설정·풀링·생명주기

**질문 11. ScriptableObject는 어디에 사용했나요?**

**답변:** 캐릭터 스탯, 공격 데이터, 소환 설정, 아이템 정의에 사용했습니다. 설정 에셋을 읽어 실행 중 사용할 값에 반영합니다. [S07·S13·S20]


**질문 12. ScriptableObject를 선택한 이유는 무엇인가요?**

**답변:** 기록된 목적은 데이터 관리와 캐릭터별 확장입니다. 공통 스탯과 캐릭터별 설정을 나누었습니다. [S07]


**질문 13. 새 공격은 전부 코드 없이 추가할 수 있나요?**

**답변:** 기존 구조의 공격 수치·애니메이션·타격 데이터는 에셋에서 설정합니다. 새로운 행동 종류까지 코드 없이 추가된다는 근거는 없습니다. [S07]


**질문 14. 오브젝트 풀은 어떻게 동작하나요?**

**답변:** v2는 적을 Queue에서 꺼내 쓰고 사망 연출 후 반환합니다. v3는 WorldObjectView와 실행 객체를 함께 재사용합니다. [S08·S13]


**질문 15. 사망 처리와 풀 반환은 같은 시점인가요?**

**답변:** v2에서는 다릅니다. 사망 이벤트로 처치·경험치를 처리하고, 사망 연출 완료 이벤트로 풀에 반환합니다. [S08]


**질문 16. 플레이어와 아이템도 모두 풀링했나요?**

**답변:** 아닙니다. v3 플레이어는 Manager의 갱신만 받고, ItemSpawnManager는 Instantiate로 아이템을 만듭니다. [S11·S20]


**질문 17. Disable과 Dispose는 어떻게 다른가요?**

**답변:** Disable은 재사용 가능한 중지이고, Dispose는 비활성화 후 마지막 정리를 한 번 수행합니다. Dispose 이후 Enable은 거부됩니다. [S13]


**질문 18. 갱신 중 객체 등록이나 반환 요청은 어떻게 처리하나요?**

**답변:** 대기 작업 목록에 넣고 현재 Tick 순회가 끝난 뒤 처리합니다. [S13]


## 코드 구조·카메라·이동

**질문 19. MonoBehaviour와 일반 C# 클래스는 어떻게 나눴나요?**

**답변:** Controller는 Inspector·Unity 이벤트 연결을 맡고, 실행 객체와 상태 클래스가 입력 소비·상태·전투 처리를 맡습니다. [S11·S12·S13]


**질문 20. Cinemachine을 선택한 이유는 무엇인가요?**

**답변:** 카메라 추적·전환·충돌 보정의 직접 구현 범위를 줄이기 위해서라고 개발 기록에 적혀 있습니다. [S10]


**질문 21. 카메라가 플레이어 회전에 끌려가는 문제는 어떻게 처리했나요?**

**답변:** CameraGroup을 플레이어 자식에서 씬 루트로 옮겼습니다. 플레이어 추적은 Follow·LookAt으로 연결했습니다. [S11]


**질문 22. 플레이어 이동은 어떤 순서인가요?**

**답변:** 입력 → 현재 상태 → 이동 방향·속도 계산 → CharacterController.Move → 실제 이동 속도 계산 → 애니메이션 갱신 순서입니다. [S10·S12]


**질문 23. 이동을 Update에서 처리한 이유는 무엇인가요?**

**답변:** 개발 기록은 CharacterController.Move를 사용하고 이동량에 deltaTime을 반영하기 때문이라고 설명합니다. [S10]


## 적의 경로와 행동 선택

**질문 24. 좀비의 NavMeshAgent가 직접 위치를 바꾸나요?**

**답변:** v3 좀비에서는 경로·회피 방향만 계산합니다. Agent의 위치·회전 자동 갱신은 끄고 실제 이동을 Movement에서 처리합니다. [S18]


**질문 25. 좀비는 매 프레임 목적지를 다시 설정하나요?**

**답변:** 첫 요청, 0.2초 갱신 시간 만료 또는 목표가 0.5m 이상 이동한 경우에 갱신합니다. [S18]


**질문 26. 좀비 상태머신은 어떤 계층인가요?**

**답변:** 상위에 생존·피격·사망을 두고, 생존 안에 대기·경계·추격·공격·귀환 행동을 둡니다. [S18]


**질문 27. NightShade는 다음 공격을 어떻게 고르나요?**

**답변:** 실행 가능한 후보의 기본 점수·거리 적합도·반복 감점·난수 보정을 계산하고 최고 점수 공격을 선택합니다. [S16]


**질문 28. NightShade의 선택과 실행은 어떻게 나눴나요?**

**답변:** Selector가 행동을 고르고, Action이 개별 동작을 구현하며, Runner가 Enter·Update·Exit 호출을 관리합니다. [S16]


**질문 29. 난수가 있는 AI를 어떻게 테스트하나요?**

**답변:** 난수 제공자를 인터페이스로 받습니다. 테스트에서는 고정 난수를 주는 구현을 사용합니다. [S16·S24]


## 공격·피해·피격 반응

**질문 30. 검이 프레임 사이를 이동하는 구간은 어떻게 검사하나요?**

**답변:** 현재 Capsule을 검사하고, 검의 시작·중간·끝점이 이전 위치에서 현재 위치로 이동한 구간을 SphereCast로 검사합니다. [S14]


**질문 31. 같은 공격에서 중복 피해는 어떻게 막나요?**

**답변:** 공격 구간별 HashSet에 피해 수신 대상을 기록합니다. 이미 기록된 대상은 다시 처리하지 않습니다. [S14]


**질문 32. 모든 공격 판정을 LateUpdate에서 하나요?**

**답변:** 아닙니다. 현재 NightShade는 LateUpdate, 플레이어는 상태머신 Update에서 공격 검출을 호출합니다. [S12·S16]


**질문 33. v2의 실제 피해 공식은 무엇인가요?**

**답변:** `max(공격력 × 200 / (200 + 방어력), 1)`입니다. README의 상수 100과 다릅니다. [S05]


**질문 34. v1에는 최소 피해 보장이 없었나요?**

**답변:** 있었습니다. 비율 감소에 20% 하한을 두고, 최종 피해도 최소 1로 제한합니다. [S05]


**질문 35. 가드 판정은 어떤 순서인가요?**

**답변:** 무효·사망과 구르기 무적을 먼저 확인합니다. 이후 가드 준비·방향·공격의 방어 가능 여부와 스태미나로 결과를 정합니다. [S17]


**질문 36. 스태미나가 가드 비용과 정확히 같으면 어떻게 되나요?**

**답변:** 양수인 가드 비용과 같으면 GuardBroken입니다. 비용보다 많아야 Blocked가 됩니다. [S17]


**질문 37. 연속 피격 애니메이션은 어떻게 제어하나요?**

**답변:** 현재보다 약한 반응의 재시작을 막습니다. SmallHit 재시작에는 0.18초 제한을 둡니다. [S17]


**질문 38. 타격 정지는 게임 전체 시간을 멈추나요?**

**답변:** CombatHitStop은 해당 유닛의 Animator와 상태 갱신을 멈춥니다. 기존 속도를 저장했다가 종료·Reset 때 복구합니다. [S17]


**질문 39. 입력 반응을 조정한 실제 변경이 있나요?**

**답변:** 67bd36e8에서 공격 중 구르기 전환을 조정하고 당시 방어 준비 기본값을 0.1초에서 0.05초로 줄였습니다. 체감 지연 측정값은 없습니다.


## 저장·인벤토리·UI

**질문 40. JSON 저장은 언제부터 있었나요?**

**답변:** v1부터 있었습니다. 96e46204에 JsonUtility와 persistentDataPath로 변경한 기록이 있습니다. [S03]


**질문 41. 저장된 게임은 어떻게 이어서 실행하나요?**

**답변:** v2는 JSON을 데이터 객체에 복원하고 저장된 씬 번호를 읽어 이동합니다. 스포너는 저장된 처치 수를 불러옵니다. [S09]


**질문 42. 저장 시스템에서 아직 확인하지 못한 것은 무엇인가요?**

**답변:** 확인한 v2 SaveSystem에는 JSON 손상·파일 쓰기 실패 복구가 없습니다. 현재 v3 인벤토리의 영구 저장 연결도 확인하지 못했습니다. [S09·S20]


**질문 43. 가방이 꽉 차도 교환할 수 있나요?**

**답변:** 비용 아이템의 마지막 1개를 써서 칸이 비면 가능합니다. 실패 시 가방을 유지하고, 성공 시 Changed를 한 번 알리도록 구현했습니다. [S20]


**질문 44. UI는 언제 갱신하나요?**

**답변:** 체력·스태미나·인벤토리 등의 변경 이벤트를 받아 갱신합니다. v3 HUD에는 유닛 해제와 비활성화 시 구독 정리가 있습니다. [S19]


## 지역 씬·미니맵·그래픽

**질문 45. 지상과 지하 씬은 어떻게 관리하나요?**

**답변:** Common을 유지하고 지역 씬을 Additive로 로딩합니다. 지역 해제 후 라이트맵을 정리하고 UnloadUnusedAssets 완료를 기다립니다. [S21]


**질문 46. 씬 해제만으로 모든 에셋 메모리가 없어지나요?**

**답변:** 현재 문서는 다른 씬·정적 필드 등이 참조한 에셋은 남을 수 있다고 설명합니다. 실제 해제량은 측정하지 않았습니다. [S21]


**질문 47. 미니맵은 현재 층을 어떻게 정하나요?**

**답변:** 플레이어 높이로 MinimapFloor를 고릅니다. 현재 층에는 경계 여유값을 적용하고, 씬 로드·해제 때 층 목록을 갱신합니다. [S22]


**질문 48. 어떤 그래픽 작업을 했나요?**

**답변:** v1에 림라이트·디졸브 셰이더와 노멀맵 수정·라이트 베이크 기록이 있습니다. 시각적 몰입감이 기록된 목적입니다. [S23]


## 테스트·성능·연동·검증 범위

**질문 49. GC 최적화는 무엇을 확인했나요?**

**답변:** 상태 재사용·NonAlloc 버퍼·캐시와 반복 할당 테스트 코드를 확인했습니다. 게임 전체 GC 0이나 Profiler 실측 결과는 확인하지 않았습니다. [S11·S14·S24]


**질문 50. 테스트 결과를 수치로 설명해 주세요.**

**답변:** 2026-08-22 문서에는 관련 테스트 39 통과, 전체 124 통과·2 실패가 기록되어 있습니다. 현재 버전은 재실행하지 않았습니다. [S15]


**질문 51. 30·60·120 FPS 검증은 어디까지 했나요?**

**답변:** 당시 기록은 보정 계산기의 요청 누적 거리 비교입니다. 실제 CharacterController 충돌 결과와 PlayMode 검증은 미확인입니다. [S15]


**질문 52. FPS가 50% 개선됐다는 근거는 무엇인가요?**

**답변:** README와 커밋에 그렇게 기록되어 있습니다. 측정 환경·Profiler 원본은 이번 자료에서 확인하지 못해 검증된 수치로 단정하지 않습니다. [S25]


**질문 53. IAP와 Steam은 어느 수준까지 구현했나요?**

**답변:** 테스트 상품 구매 요청과 결과 콜백, Steam 초기화·콜백 실행·종료 코드까지 확인됩니다. 상용 결제·출시 성과는 확인할 근거가 없습니다. [S04]


**질문 54. 책임 분리가 드러나는 부분은 어디인가요?**

**답변:** Controller와 실행 로직, AI 선택과 실행, 씬 로딩과 UI·퀘스트가 분리되어 있습니다. 경로·난수 제공자는 인터페이스로 연결합니다. [S11·S16·S18·S21]


**질문 55. 이번 분석으로 확정할 수 없는 성과는 무엇인가요?**

**답변:** FPS 개선의 원인별 기여, 메모리 절감량, 개발 시간 단축률, 현재 전체 테스트 통과 여부입니다. 해당 증거는 확인하지 못했습니다. [S15·S25]
